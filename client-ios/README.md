# stasis / client-ios

iOS backup client, using [`server`](../server) for management and storage.

This submodule is a native SwiftUI application, responsible for performing all client operations
(backup, recovery, maintenance) on iPhone and iPad.

It is made up of two parts:
* [`lib`](lib) - a Swift Package (`StasisClientLib`) with the platform-independent client core (encryption,
  packaging, operations, telemetry); shared with any future Apple targets
* [`app`](app) - the iOS application (`StasisClient`), its unit tests and a Share extension; the Xcode project
  is generated from [`app/project.yml`](app/project.yml) with [`xcodegen`](https://github.com/yonaskolb/XcodeGen)

## Development

To get started with development [`Xcode`](https://developer.apple.com/xcode/) 26 or newer (iOS 26 SDK) is needed,
along with a few command-line tools:

* [`xcodegen`](https://github.com/yonaskolb/XcodeGen) - generates the Xcode project from `app/project.yml`
* [`swiftlint`](https://github.com/realm/SwiftLint) - linting
* `python3` - runs the [`qa.py`](qa.py) QA script

```
brew install xcodegen swiftlint
```

The Xcode project is not committed; generate it (and open it) with:

```
cd app
xcodegen generate
open StasisClient.xcodeproj
```

Additionally, to allow for testing of the client itself using the iOS Simulator, the `server` and
`identity` services need to be up and running (see [`deployment/dev`](../deployment/dev) for more info).

Finally, the client itself needs to go through the usual bootstrap process before it can be used/tested.
A script that retrieves bootstrap codes can be found in the [`./dev`](dev) directory:

```
./dev/get_bootstrap_code.sh
```

> To run linting and all tests, execute `./qa.py`. Individual phases and aliases (`lib`, `app`, `ci`, ...) are
> available too; run `./qa.py --help` for the full list.

### Service Connections

Unlike the Android emulator, the iOS Simulator shares the host machine's network stack, so it reaches the dev
services exactly as the host Mac does - there is no `10.0.2.2`-style indirection. The bootstrap script points the
client at the internal service name (`https://server:20002`), so the `server` and `identity` names need to resolve
on the host (for example via `/etc/hosts` entries or a local DNS server). Once the host can reach the services, so
can the Simulator.

### TLS Certificates

By default, `server` and `identity` have TLS enabled with self-signed certificates. The iOS client has no feature
that allows accepting self-signed certificates; instead, the dev CAs should be trusted by the OS.

The [`./dev/install_dev_ca.sh`](dev/install_dev_ca.sh) script bundles the `server` and `identity` self-signed
certificates (from [`deployment/dev/secrets`](../deployment/dev/secrets)) into a `stasis-dev-ca.mobileconfig`
configuration profile:

```
./dev/install_dev_ca.sh
```

To install it on a booted Simulator:

```
xcrun simctl openurl booted "file://$(pwd)/dev/stasis-dev-ca.mobileconfig"
```

Then, in the Simulator:

1) `Settings` > `Profile Downloaded` > `Install`
2) `Settings` > `General` > `About` > `Certificate Trust Settings` and enable full trust for
   `stasis dev :: server` and `stasis dev :: identity`

On a physical device, AirDrop or email the `.mobileconfig` to the device and follow the same install/trust steps.

> The certificates are generated by [`deployment/dev/scripts/prepare_deployment.sh`](../deployment/dev); run it
> first if the script reports a missing certificate.
